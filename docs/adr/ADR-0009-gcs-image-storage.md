# ADR-0009: GCS for Image Storage

**Status**: Accepted
**Date**: 2025-11-17
**Deciders**: Claude Code, Project Lead
**Technical Story**: Sprint 0.1 - Image Storage Strategy Decision (Q5 Resolution)

## Context and Problem Statement

Project B receives `DocumentMetadata.json` from Project A, which includes references to preprocessed and corrected page images. These images are the primary input for layout detection, OCR, and structure extraction. The images are generated by Project A's IQA & Preprocessing pipeline and must be accessible to Project B for processing.

Where should these preprocessed images be stored to ensure efficient access, scalability, and integration across the 4-project RAG pipeline (A→B→C→D)? The storage solution must support both single-system deployments (local filesystem) and distributed deployments (cloud storage).

## Decision Drivers

* **Project A Integration**: Seamless integration with Project A's image preprocessing output
* **Scalability**: Support storage of millions of page images (100GB-10TB)
* **Access Speed**: <50ms image retrieval latency for real-time processing
* **Multi-System Access**: Enable distributed deployment (Project A, B on different machines)
* **Cost Efficiency**: Minimize storage costs for large document collections
* **Durability**: 99.99%+ durability to prevent image loss
* **Security**: Support access control and encryption for sensitive documents
* **API Simplicity**: Clean Python API for image upload/download
* **Backup Strategy**: Enable automated backup and versioning

## Considered Options

* **Option 1: Google Cloud Storage (GCS)** - Cloud object storage with centralized access
* **Option 2: Local Filesystem** - Store images on local disk with file paths
* **Option 3: Amazon S3** - AWS object storage alternative to GCS
* **Option 4: Azure Blob Storage** - Microsoft cloud storage alternative
* **Option 5: Network File System (NFS)** - Shared filesystem across machines

## Decision Outcome

**Chosen option**: "Option 1: Google Cloud Storage (GCS)", because it provides scalable centralized storage, seamless integration with Project A (already using GCS for image processing), <50ms access latency with Cloud CDN, and excellent Python SDK. GCS enables both single-system (GCS bucket on local network) and distributed (multi-region) deployments.

### Implementation Details

1. **DocumentMetadata Schema**:
   ```json
   {
     "pages": [
       {
         "page_index": 0,
         "corrected_image_gcs_path": "gs://project-a-images/doc123/page_0_corrected.png",
         "original_image_gcs_path": "gs://project-a-images/doc123/page_0_original.png"
       }
     ]
   }
   ```

2. **GCS Integration**:
   ```python
   from google.cloud import storage

   class ImageStorage:
       def __init__(self, bucket_name: str):
           self.client = storage.Client()
           self.bucket = self.client.bucket(bucket_name)

       def get_image(self, gcs_path: str) -> bytes:
           blob = self.bucket.blob(gcs_path.removeprefix("gs://bucket/"))
           return blob.download_as_bytes()

       def put_image(self, gcs_path: str, image_bytes: bytes):
           blob = self.bucket.blob(gcs_path.removeprefix("gs://bucket/"))
           blob.upload_from_string(image_bytes)
   ```

3. **Caching Strategy**:
   - Local cache: LRU cache for recently accessed images (reduces GCS calls)
   - Cache size: 1-5GB (configurable via environment variable)
   - Cache eviction: LRU policy (least recently used)
   - Cache invalidation: TTL-based (1 hour default)

4. **Deployment Modes**:
   - **Single-System**: GCS bucket on local network or regional bucket (low latency)
   - **Distributed**: Multi-region GCS bucket with Cloud CDN (global access)
   - **Hybrid**: Local cache + GCS fallback (optimal latency)

### Positive Consequences

* **Centralized Storage**: Single source of truth for all preprocessed images
* **Project A Integration**: Reuses existing GCS infrastructure from Project A
* **Scalability**: Handles millions of images (100GB-10TB) without performance degradation
* **Low Latency**: <50ms access with regional buckets, <100ms with multi-region + CDN
* **Durability**: 99.999999999% (11 nines) durability prevents image loss
* **Access Control**: IAM-based permissions for secure multi-project access
* **Versioning**: Built-in object versioning enables rollback and audit trails
* **Cost Efficiency**: $0.02/GB/month (Standard Storage) scales linearly

### Negative Consequences

* **Cloud Dependency**: Requires GCP account and billing (operational dependency)
* **Network Latency**: Internet-based access adds 20-100ms latency vs. local filesystem
* **Cost Accumulation**: Storage costs grow with document collection size ($200/month for 10TB)
* **Authentication Complexity**: Requires service account setup and credential management
* **Offline Processing**: Cannot process documents without internet connectivity

## Pros and Cons of the Options

### Option 1: Google Cloud Storage (GCS)

**Pros:**
* Good, because it provides centralized storage accessible across all 4 projects
* Good, because Project A already uses GCS (infrastructure reuse)
* Good, because <50ms latency with regional buckets (acceptable for real-time processing)
* Good, because 99.999999999% durability prevents image loss
* Good, because IAM-based access control enables secure multi-project access
* Good, because object versioning enables rollback and audit trails
* Good, because Python SDK is excellent (google-cloud-storage)
* Good, because it scales to petabytes without architecture changes

**Cons:**
* Bad, because it requires GCP account and billing setup
* Bad, because internet-based access adds 20-100ms latency vs. local filesystem
* Bad, because storage costs accumulate ($0.02/GB/month → $200/month for 10TB)
* Bad, because authentication requires service account credentials

### Option 2: Local Filesystem

**Pros:**
* Good, because zero latency (<1ms file read from SSD)
* Good, because zero cost (uses existing disk storage)
* Good, because simple implementation (Python pathlib)
* Good, because no authentication required
* Good, because offline processing supported

**Cons:**
* Bad, because it couples Project A and B to single machine (no distributed deployment)
* Bad, because disk capacity limits storage (expensive to scale to 10TB)
* Bad, because no built-in redundancy (disk failure = data loss)
* Bad, because no access control (filesystem permissions only)
* Bad, because manual backup required (no automated versioning)
* Bad, because difficult to share images across multiple processing nodes

### Option 3: Amazon S3

**Pros:**
* Good, because it provides centralized cloud storage (similar to GCS)
* Good, because <50ms latency with regional buckets
* Good, because 99.999999999% durability
* Good, because boto3 Python SDK is mature
* Good, because object versioning and IAM support

**Cons:**
* Bad, because it requires AWS account (different from GCP)
* Bad, because Project A uses GCS (not S3), creating multi-cloud complexity
* Bad, because storage costs are similar to GCS ($0.023/GB/month)
* Bad, because cross-cloud data transfer incurs egress fees ($0.09/GB)
* Bad, because authentication requires separate AWS credentials

### Option 4: Azure Blob Storage

**Pros:**
* Good, because it provides centralized cloud storage
* Good, because <50ms latency with regional storage accounts
* Good, because 99.999999999% durability
* Good, because azure-storage-blob Python SDK available

**Cons:**
* Bad, because it requires Azure account (different from GCP)
* Bad, because Project A uses GCS (not Azure), creating multi-cloud complexity
* Bad, because storage costs are similar ($0.018/GB/month)
* Bad, because cross-cloud data transfer incurs egress fees
* Bad, because authentication requires separate Azure credentials

### Option 5: Network File System (NFS)

**Pros:**
* Good, because it provides shared filesystem across machines
* Good, because POSIX-compliant (works with standard file I/O)
* Good, because low latency (~5-10ms on local network)
* Good, because no cloud dependency

**Cons:**
* Bad, because it requires NFS server deployment and management
* Bad, because scalability is limited (performance degrades with many clients)
* Bad, because no built-in versioning or access control
* Bad, because single point of failure (NFS server)
* Bad, because manual backup required
* Bad, because difficult to distribute across regions (high WAN latency)

**Caching Strategy**:

```python
from functools import lru_cache
import hashlib

class CachedImageStorage:
    def __init__(self, bucket_name: str, cache_size_gb: int = 5):
        self.storage = ImageStorage(bucket_name)
        self.cache_size = cache_size_gb * 1024 * 1024 * 1024  # Convert to bytes

    @lru_cache(maxsize=1000)  # Cache 1,000 most recent images
    def get_image(self, gcs_path: str) -> bytes:
        return self.storage.get_image(gcs_path)
```

**Alternative: Local Cache + GCS Fallback**:

For single-system deployments, prefer local filesystem with GCS fallback:

```python
class HybridImageStorage:
    def __init__(self, local_cache_dir: Path, gcs_bucket: str):
        self.local_cache = local_cache_dir
        self.gcs_storage = ImageStorage(gcs_bucket)

    def get_image(self, gcs_path: str) -> bytes:
        # Try local cache first
        local_path = self.local_cache / Path(gcs_path).name
        if local_path.exists():
            return local_path.read_bytes()

        # Fallback to GCS
        image_bytes = self.gcs_storage.get_image(gcs_path)

        # Populate local cache
        local_path.write_bytes(image_bytes)
        return image_bytes
```

**Future Consideration**: If GCS costs become prohibitive (>$1,000/month), consider migrating to self-hosted object storage (MinIO, Ceph) for cost reduction while maintaining S3-compatible API.
